レビューで確認した点：
- 結果記事の判定に `result_available` を一切使っていない。
- 4つの読み取り（レース情報・確定結果・出走データ・既存の結果記事）のどれかが失敗した場合や、取得件数が上限に達した場合は、例外になって結果記事だけを作らない（`collectRaceData` の try/catch）。

レビューで見つけた既存仕様（今回は変更しない）：
- `insertCandidates()` は見出しが同じ記事を重複として扱う。そのため「徳山5R 5Rの結果を更新」のように過去と同じ見出しになる結果記事は、確定済みでも作られない。誤公開の方向には働かない。
- 1日3回の実行ごとに、同じ場で別のレースの結果記事が作られ得る（従来どおり）。

- 10/13 に、締切から10分以上たって確定結果がないレースが2件あり、どちらも生成しない。
- 10/13 の実データで旧処理と新処理を比べると、結果記事以外の候補は完全に一致した。`result_available` が全件 true の状態を再現すると、旧処理は締切前の若松12Rに「結果が確定」という記事を作るが、新処理は作らない。

## PHASE C：外部同期の根本原因調査

### 確認できた事実

`result_available` を書いている経路は2つあり、互いに上書きし合っている。

| 経路 | 実行元・頻度 | 書き込む値 |
|---|---|---|
| A. pg_cron ジョブ `boatstrikers-openapi-live-3m` → `public.bs_sync_openapi_today()` → `public.bs_apply_openapi_results()` | Supabase の DB 内。3分ごと、JST 8:00〜23:30 | OpenAPI の `today.json` で `result` オブジェクトを持つレースを true にする。API は未実施のレースにも `result` を返すため、10/13 は 08:00 の時点で132件すべてが対象になり、すべて true になった（その時点で確定結果テーブルに入ったのは0件）。確定結果テーブル（bs_race_results）には3連単か1着艇があるレースだけを入れるため、こちらは正しい |
| B. 外部の Python 処理 | 約5分ごと（JST 8時台〜0時台）。API ログ上の User-Agent は `python-requests/2.34.2`。送信元は日本（大阪）の KDDI 回線で、service_role キーを使っている。運営側の手元の PC かサーバーで動いているとみられる。このリポジトリと、このセッションで見える11リポジトリには該当コードがない | `bs_race_events` に出走表の項目と `result_available` を一括で upsert する（`resolution=merge-duplicates`）。観測では false を書いていて、終了済みのレースも false に戻す。同じ処理が `bs_race_entries`・`bs_ai_bet_results` にも書き込み、`bs_ai_predictions` などを読んでいる |

- その結果、当日のフラグは数分ごとに全件 true と全件 false を行き来する。観測値は、14:30 が全件 true、18:22 が全件 false、18:45 が全件 true。
- 前日以前の分は、最後に 23:27 の A が書くため、全件 true で残る。
- ほかに `result_available` を読んで処理を決める DB 関数：
  - `bs_backfill_missing_results`：毎日 0:10・0:30・1:00 JST。true のレースで確定結果が無いものを、3連単と6艇の ST がそろっている場合に補完する。3連単とSTの条件があるため誤補完はしない。
  - `trinity_shadow_guard`：TRINITY の予測の保存を判定する。

### 影響（優先順位順）

1. **NEWS 結果記事**：締切前の誤公開。このブランチで防止できる。既存46件は PHASE B で訂正する。
2. **予想用オッズの記録**：`result_available = false` かつ締切3〜23分前のレースだけを記録する。A が3分ごとに true にするため、ほとんど記録されない（10/13 は0件、10/12 は15件）。
3. **TRINITY**：DB関数がフラグ false 以外では予測の保存を拒否する。B が false にした直後しか保存できず、件数が減っている。
4. **中止検知**：true のレースを確認しない。全件 true の時間帯は、中止・順延を記録できない。
5. **レース画面**：true なら「結果」扱いにするため、締切前のレースが結果確定として扱われ得る。確定結果テーブルを使う一覧（`racesIndexLight.js`）は影響を受けない。
6. **X投稿・NEWS候補の検証**：締切後で true なら確定と判定する。結果が出る前に確定扱いになり得る。
7. **日次まとめ・DATA LAB**：
   - 日次まとめの「全件 true」という生成条件は、事実上効いていない。B の false の直後に当たると生成を見送る可能性もある。
   - DATA LAB は翌朝の実行で、前日分は全件 true のため影響は小さい。

### 未確認の事項

- Python 処理の実体（どの PC・どのスクリプトか、何を根拠に `result_available` を決めているか）。送信内容（本文）はログに残らないため、値の決め方はこちらでは分からない。
- OpenAPI の `today.json` が未実施のレースに返す `result` の中身（空のオブジェクトか、null 項目入りか）。

### 安全な修正案（未実施）

1. **最優先・影響最小**：Python 処理の upsert から `result_available` を外す（出走表の同期は結果を知らないため）。Python 側の変更だけで、DB は触らない。
2. **DB関数**：`bs_apply_openapi_results` の bs_race_events の更新を、`result_available = e.result_available or (p.trifecta_result is not null and p.trifecta_payout is not null)` に変える。3連単と払戻が来たレースだけを true にし、いったん true にしたものは戻さない。
3. **一致の担保（中期）**：`result_available` を「bs_race_results に確定行がある」から決めるようにする。例えば、bs_race_results への挿入時に bs_race_events を true にするトリガーを置く。これは全ての書き込み経路に効くが、DB の変更範囲が大きい。
4. **段階的に進める**：まず読み取り専用のビューで「フラグと確定結果の不一致件数」を毎日監視する。1・2 を入れて不一致が0になることを確かめてから、3 を検討する。
5. **各機能**：オッズ記録・TRINITY・中止検知・レース画面は、1・2 で直る見込み。直るまでの暫定として、確定結果テーブルを根拠にする修正も可能。

### 承認が必要な作業

- Python 処理の修正（運営側の環境で行う作業）。
- DB関数 `bs_apply_openapi_results` の修正、監視ビュー・トリガーの追加（DB変更）。
- 各機能の暫定修正。
