## 構成と責任

OpenAPI → Supabase Cron → preview／確定結果。Windows v7 → BRDB／PC-KYOTEI → 従来の開催・出走表・展示等。Supabase → Next.js／Vercel → TODAY・開催一覧・出走表・番組表・結果画面。GitHub Actions → 契約テストと分離PostgreSQLフィクスチャ。切替後はデータ種別単位の出典と更新時刻を保持し、同一データへのスケジュール実行を一つに絞る。

## 次の作業と完了条件

1. **公開画面と提供元を読む。** 現行デプロイの公開ページを実ブラウザで、同日の公式開催、各場1〜12R、6艇の登録、展示、結果、払戻と比較する。未開催・中止も照合し、更新遅延、欠損、認証失敗を区別する。停止済みのWindows更新が担っていた開催・6艇出走表の保存をクラウドで引き継ぐ。PC-KYOTEIのタスク名、エクスポート手段と下流の使用列を特定する。BRDB提供元のQ009/Q011と許容頻度を照合する。
2. **古いスキーマを再現する。** 初期スキーマの履歴を検索し、作成時の正確なコミット・Migration順・分離DBでの最初の失敗を記録する。現在のスキーマを過去の初期状態として扱わない。過去の失敗ログが入手できる場合は比較する。
3. **隔離環境で取り込みをリハーサルする。** 開催日と6艇、展示・結果の出典優先順位、同時実行、再実行、途中失敗時のロールバック、RLS、アラートと精算トリガーを検証する。JSTの日替わりを通し、監視に件数・鮮度・失敗箇所を表示する。過去復元は正確なレースキーだけを対象とし、確定結果と払戻の不変性を確認する。
4. **本番切替は別承認。** DB設置、Cron切替、Vercelデプロイ、過去データ書き込みを個別に審査する。各操作に対象コミット、実行時間、書き込み対象、停止基準、切り戻し手順を添える。
5. **運用の完成を判定する。** 複数開催日で、日付切替から最終結果まで公式件数・6艇・展示・払戻が一致し、サイト公開画面の表示と認証が通る。欠損の検知、再実行、切り戻しがクラウドだけで成立した証拠を残し、Windows更新を停止した状態で運用を完結できることを確認する。
