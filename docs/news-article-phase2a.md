# BoatStrikers NEWS 記事品質改善 PHASE 2A（新旧比較 Preview と調査）

作成日：2026-10-13（JST）／ブランチ：`claude/elegant-maxwell-ha2awt`

本番DBへの書き込み・既存記事（article_body）の更新・DBトリガー・cron・収集処理・既存の NEWS 画面は変更していない。main への変更・デプロイもしていない。本番DBは読み取り（SELECT）だけ。

## 1. 新旧記事の比較画面（Preview）

- URL：`/admin/news-preview`（一覧）、`/admin/news-preview/[id]`（記事ごと）。
- 公開範囲：既存の管理画面と同じ管理者ログイン（`app/admin/layout.js`、未ログインは `/admin-login` へ転送）でだけ見られる。`<meta name="robots" content="noindex, nofollow, noarchive, nocache">` を付け、`robots.txt` でも `/admin/` は対象外。既存の NEWS 画面・管理トップからはリンクしていない（URL 直接指定のみ）。
- データ：記事・レースデータとも、公開用の anon キーで読み取る。RLS で読み取りだけが許可され、書き込みはできない（`hatsune_news` は公開記事のみ、`bs_race_entries`／`bs_race_events`／`bs_race_results` は読み取りのみ）。
- 記事ごとの表示：
  - 現在の本文（旧本文の問題を自動で表示：旧テンプレート、女子戦テンプレートの混入、出典サイトの宣伝文、途中で切れた文、収集時の定型文、AIの埋め草、本文中の出典名）
  - 新しい試作：リード文、NEWS FACT、DATA CHECK、EDITOR'S VIEW
  - 採用可否（採用可／要確認／材料不足）と品質チェックの結果
  - 照合根拠：読み取った範囲（場コード・期間・公開時刻の条件）、記事の記載と DB の照合表（一致／不一致／未確認）、使った出走データ（日付・R・艇・進入・ST・着）、読み取りエラーや件数上限の有無
- 一覧：新しい順に40件ずつ判定し、採用可・要確認・材料不足で絞り込める。

ローカルで、本番から読み取ったデータ（記事884件、11場・約1週間分のレースデータ）を返すモックを使って表示を確認した。未ログイン時の転送、noindex、PCとスマホ幅（横スクロールなし）の表示を確認済み。本番データでの表示は、Vercel の Preview で確認する必要がある（本セッションからは Supabase に接続できないため。4章参照）。

## 2. 材料不足の記事の表示案

材料不足（PHASE 1 の判定で541件）は一律に置き換えない。Preview の記事ページで、次の3案を並べて比較できる。どれも自動では適用せず、非公開にもしない。

| 案 | 表示 | 残る問題 |
|---|---|---|
| A：出典リンク＋確認済みの事実のみ | 見出し、試作で確認できた事実（あれば）、出典へのリンク | 事実が無い記事は見出しとリンクだけになる |
| B：現在の本文を維持 | 今の article_body | 定型文・女子戦テンプレートの混入がそのまま残る |
| C：詳細ページへの公開導線を抑える | 一覧から出典へ直接案内し、詳細ページへのリンクを出さない。詳細ページは残して noindex | 詳細ページを直接開いた場合は B と同じ本文 |

## 3. AI による事実抽出（設計と試験比較）

### 設計（`lib/newsArticle/aiFacts.js`）

1. 入力は、見出し（H）と、掃除済みの要約の完結した文（S1, S2, …）だけにする。途中で切れた文・収集時の定型文・出典サイトの宣伝文は渡さない。
2. AI には、事実ごとに `evidence`（入力の id と、その文から一字一句そのまま抜いた部分）を必ず付けさせる。目標・展望は `schedule`、談話は `quote` に分ける。
3. 出力は `validateAiFacts()` で機械的に検証し、通ったものだけを候補にする。
   - 根拠の引用が、指定した入力の文に一字一句含まれているか
   - 事実の文にある数値が、すべて根拠の引用の中にあるか
   - 推測・評価の表現（期待／だろう／可能性／予想 等）が無いか
   - 出典名・URL が無いか
   - 入力と25字を超えて連続一致していないか（談話は除く）
   - 目標・展望を `schedule` 以外で書いていないか
   - 談話が入力と一致するか、重複していないか
4. モデル呼び出しは外から関数として渡す。このモジュール自体は API を呼ばない。本番記事への生成・保存は行わない。

### 試験比較

- 対象：ルールでは事実を取り出せなかった189件のうち20件。新しい順に、出来事の種類（談話・優勝戦進出・予選・事故・企画）が偏らないよう選んだ。
- 実行したモデル：この環境には本番で使っている AI（OpenAI、`HATSUNE_NEWS_AI_MODEL`）の API キーが無い。そのため、同じプロンプトをこのセッションの Claude（サブエージェント）に与えて出力させた。本番想定のモデルでの結果ではない。
- 結果：20件すべてで1件以上の事実が採用された。抽出された59件のうち、検証を通ったのは47件、不採用は12件。

| 不採用の理由 | 件数 |
|---|---|
| 根拠の引用に無い数値（主に「(46=山口)」の年齢を引用の外から書いた） | 9 |
| 入力と25字を超えて連続一致（丸写し） | 2 |
| 目標（「A1昇級を狙える位置」）を達成済みの記録として書いた | 1 |

- 採用47件を人の目で確認した結果：入力に無い事実が混ざったものは見つからなかった。ただし次の2点が課題として残る。
  - 1788「準優11Rで石岡将太はカドまくりで…」は、入力の S2 に選手名が無く、前の文からの文脈でつないでいる（内容は正しい）。
  - 「太鼓判を押した」「評価している」のような、記事の評価表現を言い換えたものは通る（数値・根拠の検証では止められない）。
- 改善案：年齢・支部を引用に含めるよう指示する。選手名がその文の根拠に無い場合は、警告として扱う。

各記事の結果は付録Aに載せた。

## 4. DATA CHECK の安全性

### 実装の変更

- 照合範囲は、記事の場と公開日（6日前〜公開日）で決める。そのうえで、選手名（登録番号が1人に決まる場合だけ）、場、開催日、公開時刻（締切から20分以上たったレースだけ）がすべて合うデータだけを表示する。一意に照合できない場合は欄ごと省略する（PHASE 1 と同じ）。
- 各表の取得が上限（1000件）に達した場合は、途中までしか読めていないとみなし、照合に使わない。
- 読み取りエラー時は DATA CHECK を省略し、NEWS FACT だけで試作を続ける。
- 日次まとめは `bs_daily_result_digests` を使わず、`bs_race_events` のその日の全レースから、公開時点で確定していたレース・万舟・最高配当を数え直す。決まり手コード（`winning_technique_code`）は読まない。日次まとめの決まり手・逃げ件数は、原因（5章）が解決するまで使わない。
  - 数え直した値は、9/28〜10/12 の15日分で日次まとめテーブルとほぼ一致した。差はレース数が−1の日が2日（3連単が無いレース）、万舟が+1の日が2日。

- RLS により、anon キーでは `bs_grade_race_events` と `bs_daily_result_digests` が0件になる。グレードは引き続き「未確認」扱い。

## 5. 既存データの問題（調査のみ・修正していない）

### 5-1. 締切前に「○R の結果を更新」記事が作られる

- 対象：`lib/hatsuneNewsCollector.js` の `collectRaceData()`。cron `hatsune-news-pipeline`（10:00／14:00／22:00 JST 等）で動く。
- 発生条件：その日の女子戦のうち `bs_race_events.result_available = true` のレースから、R番号が最大のレースを選んで結果記事を作る。10:00 の実行時に、まだ締切前で3連単も入っていないレースが `result_available = true` になっている。
- 影響件数：`bs:result:*` の結果記事54件（8/28〜10/12、すべて公開中）のうち、**45件が締切前に作成**されている。45件すべてが 10:00 の実行で作られ、3連単が無い（要約が「結果が確定」だけ）。締切後に作られた9件は、すべて3連単入り。
- 原因の所在：
  - `result_available` を書いているのは、このリポジトリ外のレース同期処理（DB関数 `bs_apply_openapi_results` は 23:27 JST の結果反映で true にするが、それより前に true になっている）。
  - 過去の状態は上書きされていて、DBから遡れない。そこで 10/13 10:00 の実行直前の状態を読み取りで観測する予定（結果は追って報告する）。
  - DB には既に、`result_available` 単独を信用しない `v_bs_race_results_confirmed` ビューがある（3連単・払戻・締切5分後の条件）。ただしこのビューも `result_available OR …` なので、この問題は防げない。
- 追加の観測（10/13、読み取りのみ）：
  - 予定していた 09:58 の観測は、セッションの再起動で 14:30 JST にずれた。
  - 14:30 時点で、10/13 の132レースすべてが `result_available = true` だった。うち67レースは締切前で、73レースは3連単が入っていない。全行の `api_synced_at` が同じ 14:30:00 で、日中の同期が当日の全レースに一括で `true` を書いていると判断できる。
  - 10:00 の実行でも、新たに id 1848「徳山5R 5Rの結果を更新」が作られた（締切 10:32 の前、要約は「結果が確定した」）。同じ問題が今も続いている。
- 修正案（未実施・要承認）：
  1. 収集側の条件を「3連単（3桁）と払戻があり、締切から一定時間たっている」に変え、`result_available` 単独では作らない。
  2. 外部の同期処理が `result_available` を立てる条件を調べて直す。
  3. 既存の45件の扱い（非公開、または結果確定後の内容に差し替え）を決める。

### 5-2. 日次まとめの決まり手・逃げ件数が結果テーブルと一致しない

- 対象：`lib/dailyResultDigest.js`（cron で 23:10 JST に生成）。
- 発生条件：`bs_race_events.winning_technique_code` には、2つのコード体系が混在している。
  - 体系A（公式と同じ）：1 逃げ／2 差し／3 まくり／4 まくり差し／5 抜き／6 恵まれ
  - 体系B：1 抜き／2 逃げ／3 まくり／4 差し／5 まくり差し／7 恵まれ
  - 生成時刻（23:10）の値は体系Aで、23:27 の結果反映後は多くの日で体系Bに書き換わる。10/3・10/8 は体系Aのまま残っている。
  - 一方、`dailyResultDigest.js` の変換表は「1 抜き／2 逃げ／3 まくり／4 まくり差し／5 差し／6 恵まれ」で、どちらの体系とも合わない。
- 確認結果：
  - 日次まとめの「逃げ決着」の件数は、10/1〜10/12 の12日間すべてで、実際の**「差し」の件数と完全に一致**した（例：10/6 は逃げ28と表示、実際は差し28・逃げ87）。
  - 優勝戦で多くが「抜き」になるのは、体系Aの 1（逃げ）を「抜き」と読んでいるため。
- 影響件数：
  - 日次まとめ34日分のうち、逃げ件数が誤っている日が31日。
  - 注目レース79件のうち、決まり手が結果テーブルと異なるものが45件。
  - 日次まとめの公開記事34件のうち、「逃げ決着」行を含むものが11件、「抜き」を含むものが7件。
  - 同じ列を `winning_technique_code === "2"` で数えている `lib/dataLabSocialGenerator.js` も、体系Aが残る日（例：10/3・10/8）は誤る。
- 修正案（未実施・要承認）：
  1. 決まり手は文字の `bs_race_results.winning_technique` を使う（コードを読まない）。
  2. 生成を結果反映（23:27）の後にするか、反映完了を条件にする。
  3. 同期処理で、コード体系を1つにそろえて保存する。
  4. 既存の日次まとめと記事の再生成・訂正の扱いを決める。
