## 1. マイグレーション2本の点検結果
| ファイル | 内容 |
|---|---|

### 確認したこと
すべて PGlite でテストした（`tests/blog/aiMigrationCompat.test.mjs` ほか。全128件合格）。

- **`blog_release` の差し替えは最小限**：既存の 20261003 版との違いは3か所だけ。
  1. 変数を1つ追加。
  2. AI 下書きなら、承認を確認する。
  3. 公開記録に承認 ID を入れる。
- **人が書いた記事の公開・予約・取り消し・予約公開は、これまでと同じ動作。**
  - AI 下書きの記録が無い記事では、承認の確認は一切行われない。
  - 既存の DB テスト（記事の作成・保存・公開・予約・画像公開）を、AI マイグレーションを足した状態でも実行した。結果は 20261003 適用後の状態と同じで、想定外の差は無い。
- **既存の BLOG テーブル・関数のアクセス規則は変わらない**：適用前後で次を比べ、一致した。
  - anon・authenticated の表・列の権限
  - RLS の有効化
  - ポリシー
  - 関数の実行権限と SECURITY INVOKER
- **既存の表の列の変更**：`blog_publication_events.ai_approval_id`（null 可）の追加だけ。
- **カテゴリーの変更**：3つの追加と、DATA LAB の表示名だけ。**表示名の変更は、適用した時点で公開サイトに反映される**（デプロイを待たない）。
- **新しい表**：RLS が有効、ポリシー無し、anon・authenticated への権限無し。新しい関数も service_role だけが実行できる。
- **適用前の安全装置（今回追加）**：次のどちらかなら、例外で止まり何も変更しない（テスト済み）。
  - 適用先の `blog_release` の本文が、リポジトリの 20261003 版と一致しない（リポジトリ外で変更されている）。
  - 20261003 が未適用。
- **公開時の本文照合**：AI 下書きの公開時に、次の2つを両方確かめる。
  - 承認が現在の版（編集版の番号と版 ID）に対するものであること。
  - 承認時の本文の照合値（`document_md5`）が、現在の本文と一致すること。通常の保存を通らずに本文やタイトルが変わった場合も、`BLOG_AI_CONTENT_CHANGED` で拒否する。
  - 管理画面の「承認済み」の表示も、同じ照合値で判定する。
  - **承認のたびに、承認した本文そのものを承認履歴に保存する**（照合値と一致しない本文は記録できない制約付き、追記専用）。再承認の前に承認した版の本文も残る。
- **戻し手順**：`ops/blog/ai-drafts-rollback.sql`（マイグレーションではない）。
  - **履歴は削除しない**：AI 用の8つの表をデータごと、外部から見えない保管用スキーマ `blog_ai_archive` へ移す。保管先は service_role の読み取りのみで、承認履歴の追記専用は維持される。公開記録の承認リンクも、保管先にコピーしてから列を外す。
  - 公開側の表・関数・権限は、適用前の状態に正確に戻ることをテストした。
  - 次の場合は何も変更せずに止まる：
    - 未公開・編集中・予約中の AI 下書きがある（戻すと承認の確認が消え、承認なしで公開できてしまうため）。
    - 保管用スキーマがすでにある（前回の保管を上書きしない）。
    - AI 用の表が無い。
  - **参照先の写し**：保管の時点で、次を `blog_ai_archive` に写し取る。後から公開側の行が変更・削除されても、保管した履歴の監査・追跡ができる。
    - `post_snapshot`：記事の slug・状態・公開日時と、公開中の本文・その照合値。照合値が承認時の照合値と一致すれば、承認した内容がそのまま公開されたことの証明になる。
    - `category_snapshot`・`author_snapshot`・`media_snapshot`：カテゴリー・著者・関連画像の情報。
  - **残る制約**：
    - 画像ファイルそのもの（Storage の中身）は写さない。保管するのは情報（パス・説明・出典）だけ。
    - 外部の公式ページそのものも写さない。保管するのは取得した本文・取得日時・ハッシュだけ。
- **トランザクション**：既存の BLOG マイグレーションと同じく `begin; … commit;`。途中で失敗すれば全体が取り消される。
- **一度だけ適用する**：同じファイルを2回適用すると、表の作成で失敗する（何も変わらずに止まる）。

### 運用上の注意
- **マイグレーション履歴の記録**：既存の BLOG マイグレーションと同じ方法で適用し、`supabase_migrations.schema_migrations` に同じバージョン番号（`20261009180000`・`20261010090000`）で残す。SQL Editor に貼って実行すると履歴が残らず、後で「未適用」と誤って表示される。
- **PostgREST の定義の再読み込み**：Supabase は DDL の後に自動で再読み込みする。API で新しい表が見えない場合は、ダッシュボードの「Reload schema」で再読み込みする。

## 2. ステージングでの試験手順
### 2-1 適用前（読み取り専用）
1. Supabase で **`boatstrikers-blog-staging`** を開く。画面上部のプロジェクト名が正しいことを確かめる。
2. SQL Editor で `ops/blog/ai-drafts-precheck.sql` を実行する。
   - **全行が true** なら次へ進む。1つでも false なら中止し、結果を共有する。
3. 次を記録する（件数だけ）：
   - `select state, count(*) from public.blog_posts group by state;`
   - `select count(*) from public.blog_publication_events;`

### 2-2 適用（承認後）
4. `20261009180000_blog_ai_drafts.sql` → `20261010090000_blog_ai_followups.sql` の順に適用する。
5. `ops/blog/ai-drafts-postcheck.sql` を実行し、**78行すべてが true** であることを確かめる（表8つ×6項目、関数5つ×5項目、その他5項目を個別に判定）。
6. 2-1 の件数が変わっていないことを確かめる。

### 2-3 プレビュー環境での試験（承認後）
**前提**：ブランチを Push し、そのブランチ用のプレビュー環境に変数を設定する（4 を参照）。

| # | 操作 | 期待する結果 |

| T14 | 試験後の片付け | 試験記事は非公開のまま残すか、試験記事として記録する。必要なら戻し手順の試験（任意） |

## 5. 本番の既存記事・公開機能を壊さない移行手順
**大原則**：DB の変更（追加だけ）→ コードのデプロイ（AI 機能は無効）→ AI 機能の有効化 → 定時実行、の順に、1段ずつ確かめてから進む。

1. **接続先の確定（読み取り）**
   - Vercel の Production の `BLOG_SUPABASE_URL` を確認する。URL の中のプロジェクト ID だけを見る（キーは見ない）。
   - それが `rzosrbkyniyedolhkgxo` か、別のプロジェクトかを確定する。
2. **事前の記録（読み取り）**
   - 本番の BLOG で `ai-drafts-precheck.sql`（全行 true）と、2-1 の件数を記録する。
   - Supabase のバックアップ（日次、または PITR）が直近で成功していることを確かめる。
3. **DB の適用（承認後）**
   - アクセスの少ない時間帯に、2本を順に適用する。
   - 追加される列は null 可なので、表の書き換えは起きない。
   - `blog_release` の差し替えは一瞬で終わる。
   - 直後に `ai-drafts-postcheck.sql` を実行し、件数が同じであることを確かめる。
   - DATA LAB の表示名は、この時点で公開サイトに反映される。
4. **公開サイトの確認（読み取り）**
   - ブログのトップ、既存の記事、カテゴリー一覧、サイトマップが表示されることを確かめる。
5. **コードのデプロイ（承認後）**
   - main へマージして Production にデプロイする。`BLOG_AI_DRAFTS_ENABLED` は未設定（無効）のまま。
   - この時点で変わるのは、管理画面に「AI下書き」画面と「表紙とSNS・note原稿」パネルが出ること、カテゴリー一覧に新しいカテゴリーが出ること。
   - 人が書いた記事の公開は変わらない。
6. **AI 機能の有効化（承認後）**
   - `BLOG_AI_DRAFTS_ENABLED=true` にする。最初の1記事は手動で生成し、確認・承認・公開まで通す。
7. **定時実行（承認後）**
   - `vercel.json` に `/api/cron/blog-ai-drafts` を追加し（コードの変更）、`BLOG_AI_SCHEDULE_ENABLED=true` にする。
   - 最初は1日1回・1件。テーマの自動選択は、慣れてから `BLOG_AI_SCHEDULE_AUTO_TOPICS=true` にする。
8. **戻すとき**
   - コード：Vercel の Instant Rollback で直前のデプロイに戻す。
   - AI 機能だけ止める：`BLOG_AI_DRAFTS_ENABLED` と `BLOG_AI_SCHEDULE_ENABLED` を外す（DB はそのままで安全）。
   - DB まで戻す：`ops/blog/ai-drafts-rollback.sql`（承認後。AI の履歴は保管用スキーマに残す。未公開の AI 下書きがあれば止まる）。
