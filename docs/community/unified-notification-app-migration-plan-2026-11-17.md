# BoatStrikers 通知・会員統合方針（A案）— 2026-11-17

## 決定済み方針
ユーザー承認：**BoatStrikersアカウントへ集約**し、LINE・Discord登録は必須にしない。将来はiOS/Androidアプリへの移行を目指す。既存通知の即時停止や連携削除は承認されていない。

## プロダクト体験
- 未登録：公開RACE/BLOG/掲示板を閲覧。
- 共通ログイン：投稿、返信、お気に入り、通知設定を利用。SNS外部アカウントの登録を要求しない。
- 有料機能：同一会員IDを使う。ただし有料権限は**検証済みサーバー課金情報**から判断。プロフィールplan/beta_memberを信用しない。
- 通知：サイト内受信箱を正本に、希望者だけPWA Web Push。LINE/Discordは移行期間の任意レガシーチャネル。
- iOS PWAではホーム画面への追加と通知許可が必要な場合がある。ブラウザ/OSの条件によってプッシュ未対応や配信失敗があり得るため、受信箱で取りこぼしを補う。

## 将来のネイティブアプリを見据えた境界
1. Supabase AuthのユーザーIDを共通識別子にする。プラットフォームごとに別会員を作らない。
2. 通知イベント（例：thread_reply、prediction_published、favorite_racer_update、service_notice）と配信先（in_app、web_push、将来のapns/fcm）を分離。
3. イベント生成はサーバーで認可・重複防止・保存。クライアントから他人宛の通知や有料通知を直接作成させない。
4. 通知設定はユーザー単位・種別単位。マーケティング通知は明示オプトイン。重要なお知らせは受信箱に残す。
5. Web Push購読トークン、将来の端末トークンはユーザー所有・失効・再登録・ログアウト時の扱いを設計。生トークンをログや公開APIに出さない。
6. 返信通知は投稿公開・スレッド状態・ブロック/退会状態・閲覧権限を配信時にも検証。本文に機密情報を含めない。
7. 既存LINE/Discordは利用者と依存処理を棚卸ししてから段階移行。データの無断削除・通知停止をしない。

## 実装順序とゲート
- P0 調査：LINE/Discord送信元、会員登録導線、ユーザーID紐付け、既存通知一覧、実際の通知要件を洗い出す。
- P1 API/DB設計：notifications, notification_preferences, push_subscriptionsの権限・RLS・保持期間・重複排除を定義。**まだ本番作成しない**。
- P2 サイト内受信箱を最初に提供。返信・公開記事・予想通知は権限と配信対象をテストする。
- P3 PWA Web Pushは許可画面・購読/解除・実機検証（iOS/Android）後に段階公開。
- P4 利用率・到達率・失敗率を比較し、LINE/Discordの任意化と廃止可否を個別判断。
- P5 アプリ：同じ認証・通知イベントAPIを利用し、APNs/FCMなどを追加する。App Store/Google Play審査や課金規約は実装時点で再確認。
